## Summary

Add admin-only single-warehouse stock reads and append-only receipt/issue history. PostgreSQL owns balances, movements and 24-hour idempotency outcomes. One transaction acquires a nonblocking database key lock, serializes each product balance and commits balance/movement/result together. Replays preserve original responses; in-flight duplicates immediately return the agreed 409. History joins current product metadata without catalog snapshots.

Confirmed decisions are unchanged: inactive products allow both movement types; writes require idempotency keys; duplicate in-flight requests return immediate 409 with retry; history uses immutable productId/current name/SKU; quantities/balance limits/pagination/order/auth follow the spec; no frontend, orders, external distributed locks, queues or new automated test files.

## Phase 1 — Database, API and transaction design

See [data-model.md](data-model.md) for exact columns/constraints/indexes/relationships and the ordered transaction protocol; [contracts/inventory-api.md](contracts/inventory-api.md) for endpoint envelopes/errors/idempotency lifecycle; [quickstart.md](quickstart.md) for future validation.

- Three tables: inventory_balances (logical missing row = zero), stock_movements (immutable API facts), inventory_idempotency_results (completed status/body only). No warehouse table, catalog snapshot or processing lease.
- Scope `(actor_id, inventory.movement.v1, key)`, canonical SHA-256 includes product/type/quantity/trimmed reason. Retain 201 plus deterministic product/stock failures for 24 hours; no expiry extension. Expired keys execute anew even if cleanup is late.
- Nonblocking pg_try_advisory_xact_lock returns IDEMPOTENCY_IN_PROGRESS immediately when unavailable. READ COMMITTED + balance FOR UPDATE serializes distinct commands on the same product. One connection/manager owns every write. A pre-balance savepoint removes any initialization from business-rejected commands while permitting error-result commit.
- Success writes stock, movement and original response atomically. Return business errors only after error-result commit. SQL awaited by the service that fails before commit and confirmed rollback leave no mutations; lost response/COMMIT acknowledgment remains uncertain and reconciles by same-key retry without claiming stock is unchanged. Verify API timeout 503 directly on port 3001; Gateway may return 502 first with its existing five-second timeout. No internal retry loop.
- Read-only REPEATABLE READ keeps paginated items/count consistent per request. Product ID ascending; history createdAt/id descending, timestamp assigned monotonically per product after row lock. Current product data is joined at read time.
- Fixed cleanup: hourly `0 0 * * * *` UTC, 1,000 rows/batch, at most 20 batches/run. Each batch selects expired rows ordered expires_at/id FOR UPDATE SKIP LOCKED and deletes those IDs in one short transaction. No scan/delete of movements. Per-process overlap guard, skip locked across instances, shutdown stops between batches and waits for current batch, failed runs retry next hour. Log only counts/duration/failure category, no key/body/reason/user credentials. Backlog can persist; logical expiry does not depend on deletion. No new config variables or environment-example change needed.
- Observability: emit one structured outcome event via the existing logger for each validated movement attempt reaching key ownership. For a known outcome, emit after transaction end; for lost acknowledgment emit outcome_uncertain after connection discard/release, without asserting that the server committed or rolled back. Outcomes are `completed` (only after confirmed terminal-result commit, including cached business rejection), `replayed`, `in_progress`, `conflict`, `transient_failure`, `persistence_failure` (confirmed rollback), or `outcome_uncertain` (lost COMMIT acknowledgment). Include outcome, sanitized HTTP status/error category and optional server request/movement ID; event counts provide completed/replayed/in-progress/conflict counts without a new metrics/tracing stack. Never emit completed on uncertain commit or count a replay as a new movement. Keep bounded cleanup count/duration summaries. Do not log raw key, fingerprint, reason, payload, token, cookie, credentials, SQL or connection details. T016–T017 own outcome logging, T021 owns cleanup summaries and T040 verifies both.
